## What This Project Is

Overworld Node Map is a web app for generating, editing, and exporting node-graph overworld maps for tabletop RPGs. Locations are nodes; routes between them are compass-direction edges (N/NE/E/SE/S/SW/W/NW), some of which require a skill check to pass. There are no coordinates and no real scale — the graph *is* the map. Full rationale, the MUD/hex-map inspiration, the node-type taxonomy, and the generation-to-edit design arc live in [docs/overworld-map-concept.md](docs/overworld-map-concept.md) — read it once for the "why" before touching code that shapes user-facing behavior.

## Architecture — Why the Layers Are Shaped This Way

The spec (Section 2) defines three strict layers inside `frontend/src/`: **Core** (`core/`), **Store** (`store/`), **UI** (`components/`). The boundary rules there are absolute — treat a violation as a bug. This section explains the reasoning so the boundary stays meaningful as the app grows, including why a fourth piece (the backend) exists at all:

**Core must stay deployment-target-agnostic.** Everything in `core/` (RNG, compass math, graph algorithms, the generator, the validator, the exporter) is pure, side-effect-free, and touches nothing browser-specific — no DOM, no `localStorage`, no `window`. That's not just a testability nicety: it's what let this same code get duplicated into `backend/src/core/` and run unchanged inside a Lambda (Node runtime) with zero modification. Keep it that way even when it would be more convenient to reach for a browser API from inside `core/`.
  - Concretely: `crypto.randomUUID()` and `seedrandom` are fine — both work identically in modern Node and browsers. Anything that only exists in one runtime does not belong in `core/`.

**Why hide the core behind a Lambda at all?** So the generation algorithm — the placement weights, the edge-building heuristics, the name lists — isn't sitting in the browser bundle for anyone to open devtools and read. This hides the *algorithm*, not the output: the `WorldMap` JSON shape, the validator's invariants, and the exporter all still ship client-side (they need to, for editing and export to work offline-ish). Calibrate expectations accordingly — it raises the bar, it doesn't make the generator secret in an absolute sense.

**`backend/src/core/` is an intentional duplicate, not a shared package — for now.** The spec (Section 14) is explicit that this is deliberate short-term duplication to keep the Lambda self-contained, with an explicit escape hatch: if keeping the two copies in sync becomes a burden, extract to a shared workspace package. Until that happens: `generator.ts`, `rng.ts`, `naming.ts`, `validator.ts`, `compass.ts`, and `graph.ts` in `backend/src/core/` (plus the standalone `nameforge/` library naming.ts depends on) must mirror `frontend/src/core/`/`frontend/src/` exactly, and `ALGORITHM_VERSION` must match across both. After M7, `frontend/src/core/generator.ts` (and `rng.ts`) become dead code paths in the running app — the store calls the API instead — but they stay in the tree; don't delete them as "unused." (`core/names.ts`, the pre-M4.12 placeholder for this, was genuinely retired — see M4.12's notes — not just marked dead.)

**Store is the client-specific seam.** `frontend/src/store/` is where browser concerns actually live: `localStorage` persistence, undo/redo history, selection state, orchestrating calls into `core/` (M0–M6) or the API client (M7+). This is deliberately the *only* layer that changes when generation moves off the client — swapping a direct `generateMap()` call for `generateMapApi()`. Core wouldn't change. UI wouldn't change. That's the point of drawing the line here.

**UI is a pure function of Store state.** `frontend/src/components/` renders what the store gives it and dispatches actions back into it. It never calls `core/` directly and never derives map data inline — that logic belongs in a store selector or in `core/` itself. The "node reference" (the `WorldMap` object) is the one source of truth the UI observes; components stay simple because they're not carrying business logic.

Keep functions in `core/` small, pure, and independently testable — same inputs, same outputs, no hidden state, randomness only via an injected `RngFn`. This is what makes the generator's pieces (placement, edge-building, check-marking) reusable and safe to recompose later, and it's what makes the Lambda-portability story above actually true rather than aspirational.

## Development Workflow

- **Test-driven.** Every `core/` function gets unit tests alongside it (see spec Section 15 for what each test file must cover). Don't consider a function done until its tests exist and pass.
- **Build in milestone order** (spec Section 16: M0 → M7). Don't start a milestone before the previous one's acceptance criteria pass. Each milestone must leave the app in a working, runnable state.
- Run `cd frontend && npm test` (vitest) before declaring any milestone complete and show the output.
- Favor small, independent, composable pure functions over classes or deep inheritance — this is what the spec's generator design and the reusability goal (especially around the "random" generation logic) depend on. Don't introduce an abstraction until a second real use case needs it.
- No speculative features, no unrequested refactors, no half-finished edit paths. If the spec's editing UI is "intentionally basic" for a milestone (see concept doc's Generation-to-Edit Arc), build it basic — don't gold-plate ahead of schedule.

## Notes on M4.13 (name generator test page — `/nameGenerator`)

- **This is the app's first real client-side route, and that has a Netlify-specific consequence that's easy to miss until someone hits refresh in production.** A static host serves whatever file matches the URL path literally — `/nameGenerator` has no corresponding file, so without a rewrite rule it 404s on a direct visit or hard refresh even though client-side routing handles it fine for in-app navigation. Added `frontend/public/_redirects` (`/* /index.html 200`, Vite copies `public/` verbatim into `dist/`) proactively rather than waiting for a bug report — this is the standard fix for exactly this failure mode on Netlify. If more routes get added later, this file needs no changes; it's a catch-all.
- **A real reproducibility bug was found and fixed during implementation, not just designed around up front — worth understanding before touching `pages/nameGeneratorBatch.ts`.** `generateName(theme, rng)` (nameforge) draws `rng()` *twice* in sequence: once to pick which pattern to use, then once per slot to fill it. The tool's "random pattern" mode uses `generateName`, but naively trying to reproduce one result later via `generateFromPattern(theme, result.patternId, makeRng(result.seed))` — using the pattern id that was actually rolled — skips that first draw entirely, desyncing every subsequent slot draw. The result: a *different* name, from the *same* recorded pattern id and seed, silently wrong in a way that would only surface as "huh, that didn't reproduce" much later. Caught by writing a direct reproduce-and-compare check while verifying the page, not by any test written in advance.
- **The fix is a `patternForced: boolean` flag recorded on every result**, and a single `reproduceResult(theme, result)` function that dispatches on it — `generateFromPattern` when `true`, `generateName` when `false` — rather than ever assuming "same pattern id" is enough information to replay a result. This is now the one and only place that knows how to reproduce a result; don't add a second ad hoc reproduction path elsewhere.
- **`pages/nameGeneratorBatch.ts` is deliberately a plain, framework-free module, not inlined into `NameGeneratorPage.tsx`.** The reproducibility bug above is exactly the kind of thing that's easy to get subtly wrong and hard to notice in a UI — pulling the batch/reproduce logic out into its own file made it unit-testable (`tests/pages/nameGeneratorBatch.test.ts` has a dedicated regression test asserting every row in a "random pattern" batch reproduces from its own metadata alone), which is what actually caught this class of bug being reintroduced after the fix, not just at the moment it was first found. This project has no component-test infrastructure (Vitest's environment is `node`, no jsdom/RTL) — extracting pure logic out of `.tsx` files like this is the way to get real test coverage on a page without adding that infrastructure.
- **Each batch result gets its own independent seed (`baseSeed + index`), not one shared RNG stream walked across the whole batch.** This is what makes "reproduce just this one row" possible from `{themeId, patternId, patternForced, seed}` alone — a shared-stream design would require replaying every earlier row first.
- **`makeRng`/`RngFn` (`core/rng.ts`) are re-exported from `store/mapStore.ts`** — same "component-safe seam" already used for `centroid`/`convexHull`/`isOutpostBranch`/etc, since `components/`/`pages/` may not import `core/` directly (spec Section 2). nameforge itself needed no equivalent treatment; it was already directly importable (it isn't `core/`).
- **Reachable in production by explicit user choice, not dev-gated** — an informed, scoped exception to the project's "hide the algorithm's internals from the browser bundle" precedent (the reason the whole M7 Lambda migration exists). This exception is specifically about *names*, which are cosmetic flavor, not the core placement/edge-building algorithm that precedent actually protects — don't extend this reasoning to justify exposing generator internals the same way without a similar explicit conversation.
- **`react-router-dom` is a genuinely new dependency**, added deliberately rather than a hand-rolled `window.location.pathname` check, since the user confirmed routing is now a recurring need, not a one-off. `App.tsx` is now purely route registration; the previous root layout moved unchanged into `pages/MapApp.tsx`.

## Notes on M4.12 (generated names — nameforge library + naming pass)

- **Naming is a separate post-generation pass, deliberately mirroring `layoutRelax.ts` (M4.10)'s shape** — a standalone function `generateMap()` calls at one seam in its pipeline, over already-classified nodes, that knows nothing about geometry, edges, or which placement algorithm ran before it. This was a real architectural fork the user asked to think through explicitly before building: baking name generation directly into node classification (rejected — couples two concerns the user specifically wanted kept apart) vs. formalizing `generateMap()` as a generic, introspectable "step pipeline" with naming as just one registered step (rejected — real infrastructure investment beyond what one more pass needs; `generateMap()` is already a clear, readable sequence of plain calls, and nothing else pending needs a generic pluggable pipeline). If a third or fourth post-placement pass shows up later, *that's* the point to revisit whether a formal pipeline abstraction earns its keep — not before.
- **`frontend/src/nameforge/` is genuinely standalone, not just "in its own folder."** Nothing in it imports from `core/`, `types/map.ts`, `store/`, or React — verified by construction (its only imports are within itself). `core/naming.ts` is the sole bridge, translating `MapNode`/`Biome`/`RngFn` into calls against nameforge's generic `Theme`/`Rng` API. This is what makes "copy the folder + add a `package.json`" a truthful extraction story rather than an aspiration — read `frontend/src/nameforge/README.md` before adding a new theme or touching the slot/pattern engine.
- **Themes are plain exported `Theme` constants, not a registry.** No `registerTheme()`, no global state, no string-based theme lookup inside the library itself — `core/naming.ts`'s `themeForNode()` is the only place that maps a node's classification to a theme object. Keep it that way; a registry would be speculative infrastructure for a library with exactly one consumer today.
- **The `parts: string[]` field on `GeneratedName` (not just the joined `text`) is the entire mechanism behind `rerollSlot`/reroll-one-piece** — no separate provenance tracking needed. A slot's own definition (from `pattern.slots[i]`) is enough to redraw `parts[i]` in isolation. If a future UI wants per-piece reroll on node labels (not built yet — only the map-name field's whole-name 🎲 button exists), this is already there to call.
- **`classifyNode`/`createLabelGenerator`/`nextLabel` (`generationShared.ts`) were deliberately left untouched.** They still assign a `"Village-1"`-style placeholder during classification; `applyNodeNames` unconditionally overwrites it afterward. This keeps the change small and isolated — classification's own tests/behavior are unaffected — at the cost of one wasted (but `rng()`-free, so harmless) placeholder string per node. Don't "clean this up" by threading nameforge into classification itself; that's the exact coupling the post-generation-pass design was chosen to avoid.
- **`core/names.ts` was deleted, not left as a second naming system.** It was already dead code (zero import sites) with a header comment explicitly reserving it for "a future 'randomize name' feature" — nameforge + `core/naming.ts` *is* that feature, done properly. Its water-feature name list inspired (not copied verbatim into) nameforge's `waterFeature` theme.
- **`generateName`'s (and `regenerate`/`rerollSlot`'s) default `rng = Math.random` is a deliberate exception to `core/`'s "no bare `Math.random`" rule** — because nameforge isn't `core/`, it's an intentionally-standalone library outside that boundary, the same way any third-party npm RNG-consuming package defaults to `Math.random` when the caller doesn't supply a seed. `core/naming.ts` always passes the app's own seeded `RngFn` explicitly, so this default is never actually exercised from inside the app itself — full determinism-by-seed is preserved in practice.
- **`setMapName`/`rerollMapName` (`mapStore.ts`) don't push undo/redo history** — same category as `updateDraftParam`/`randomizeSeed`/the region-preset actions: metadata, not a graph edit. `rerollMapName` calls nameforge directly with no `rng` argument (falling through to its `Math.random` default) rather than routing through `core/naming.ts`'s seeded `generateMapName` — it's a live, one-off UI convenience, not part of reproducible generation, exactly the same category as `randomizeSeed`/`randomizeRegionPreset` already using `Math.random` straight in the store.
- **`ALGORITHM_VERSION` → `2.5.0`** — a genuine new capability, not a tweak: naming consumes `rng()` draws (several per node plus one for the map name) that never existed before, so every seed's node labels and map name are new even though topology/positions are unchanged. No `PARAMS_CODEC_VERSION` bump — share codes only encode `GenerationParams`, and naming is unconditional with no new tunable/opt-out field (matching the project's existing "no speculative mode field" preference — same reasoning region presets and `applyRecommendedGridSize` already established).

## Notes on M4.10 (layout relaxation — the post-placement visual pass)

- **Force order is the whole design, and getting it wrong is silently worse than doing nothing.** The pass runs a magnetic (direction-aligning) force and a separation (spacing) force. Implemented as two *competing forces*, separation loses to the magnetic pull and crowding gets **worse** — measured on radial output, minimum node separation fell from 0.016 to 0.005 and crowded pairs tripled. Implemented with separation as a **constraint projection applied after** the force step (and not scaled by the cooling schedule), spacing becomes a hard guarantee that holds at any direction weight. This is exactly why the overlap-removal literature (PRISM, Voronoi cluster-busting, GTree) treats spacing as post-processing. Don't "simplify" this back into one summed force loop.
- **`layoutNodeSpacing` must sit below a typical edge length, and this is counter-intuitive.** The first default was 1.0 — the same as radial's natural step — which forced *every* pair (not just neighbours) at least a full step apart and reshaped the entire map. Direction accuracy got *worse* than not running the pass at all (radial 1.803 -> 1.918 rad). At 0.6 it only separates genuinely-crowded nodes: crowding still hits zero, and direction error improves in both algorithms. If someone raises this default "for more breathing room," re-measure direction error before believing it helped.
- **The measured wins, so regressions are detectable**: mean absolute angular error between an edge's declared direction and its real bearing, summed over 8 seeds — grid 1.482 -> 0.41 rad (-72%), radial 1.803 -> 1.57 (-13%). Radial gains less because weighted-random growth starts with far more mismatch. `tests/core/layoutRelax.test.ts` asserts both the direction improvement and a hard spacing floor rather than just "doesn't crash."
- **Invariant 4 (boundary placement) is the only invariant node movement can break**, so `pushOutOfForbiddenBox` runs on every position write rather than as an after-the-fact check. Any new force added here must go through the same `settle()` helper or it will eventually produce a boundary-marked node inside the forbidden inner band.
- **Several existing tests had to be pinned to `layoutRelaxStrength: 0`**, not because they broke, but because they assert *placement* contracts the visual pass legitimately perturbs afterward: radial's core-at-exact-centre test, the `repairConnectivity` edge-length regression, and M4.9's hamlet-size test (which counts nodes huddled within 0.5 units — a signature relaxation deliberately erases by normalizing spacing). When a placement-level assertion starts failing after a visual-pass change, check whether it should be isolated this way before "fixing" the pass.
- **Zero RNG.** `relaxLayout` takes no `RngFn` and consumes no draws, so adding it shifted no other generation decision — the only output difference is node positions. That's what made `layoutRelaxStrength: 0` a provable no-op and kept the whole change auditable.

## Notes on M4.9 (fine-tuning params — hardcoded constants made adjustable)

- **The governing rule: every new param defaults to exactly the value its behavior was hardcoded to.** That's what makes this a pure capability addition rather than a behavior change — the full test suite (including every determinism and "identical structural output" test, for both placement algorithms) passed unchanged after the extraction, which is the real proof. `ALGORITHM_VERSION` deliberately did **not** bump: no RNG call sequence changed. If you add another param here and a determinism test starts failing, the default is wrong, not the test.
- **Preserving the RNG call *count* matters as much as the value.** `radialClusterMaxSize` replaced `rng() < 0.5 ? 2 : 3` with `randInt(rng, 2, max)` specifically because `randInt` consumes exactly one `rng()` draw and returns the identical value for the identical draw at max=3 — a formulation that consumed two draws would have silently shifted every subsequent decision in the map.
- **Five of the eleven are shared across both placement algorithms** (`maxLargeSettlements`, `roadFraction`, `coastalChance`, `interiorBoundaryDamping`, `wildernessCheckMultiplier`) because they live in `core/generationShared.ts`'s taxonomy logic, which has nothing to do with placement geometry. Threading `params` into `connectionTypeFor` meant threading it into `ensureMinimumDegree`/`repairConnectivity` too, since those construct edges. Don't duplicate these per-algorithm if more get added — the shared module is the point.
- **`radialRimFraction` moves two thresholds, not one.** The "mid" band's inner edge scales proportionally with the rim (`MID_TO_RIM_RATIO = 0.5 / 0.85`) so the bands keep their relationship as the rim moves. A fixed inner threshold would invert (mid below center) once the rim dropped under 0.5.
- **Each knob has a test proving it actually does something**, not just that it doesn't crash — e.g. `radialJitter` is measured by deviation from the step lattice, `radialRimFraction` by boundary-marker count, `radialClusterMaxSize` by how many nodes sit within 0.5 units of a neighbor. When a knob is added, add the observable-effect test; this suite has already caught one knob (the original `radialBranchChance` burst mechanic) that measured as having literally no effect.
- **The Advanced section is collapsed by default and the radial-only half is conditional** on the selected generation style, so the panel doesn't grow unboundedly as more knobs arrive.

## Notes on the M4.8 radial-algorithm correction (rigid spokes → organic maze growth)

**The first M4.8 implementation was rejected by the user as "not shippable" after direct testing, and its growth mechanics were replaced end to end.** Read this before touching `core/radialGenerator.ts` — several of these were found only by running the thing and looking at it.

- **The original bug, precisely:** every growth step called `bestAvailableDirection` with an "ideal" of *continue the way this spoke started*, so each spoke snapped to whichever free direction was closest to its original heading — producing straight rays out of the hub. The user's feedback was blunt and specific: there should be **no** preference to continue in the same cardinal direction, direction freedom should be wide open (5-6 directions available even 2 steps out, ~7 beyond that), only a *soft* bias against heading back toward the center, and the algorithm needs real collision handling — "if it gets back close to other nodes it should just decide if we connect or not...and then decide if we head back in another direction."
- **It's now a Growing Tree maze algorithm** (the well-known unification of recursive-backtracker/Prim's maze generation — the user explicitly suggested researching maze algorithms, and this is what that turned up). Keep a frontier of growable nodes; each iteration pick one and grow. **Direction choice is weighted-random over every free direction, weighted only by `0.15 + circularDist(d, inward)`** — there is deliberately *no term whatsoever* for matching the incoming heading. If you ever find yourself adding one "to make paths smoother," that is literally reintroducing the original bug. There's a regression test for this (`does not prefer continuing straight through a node`) asserting the fraction of degree-2 nodes whose two exits are exactly opposite stays near chance (~0.16 observed, ~0.14 theoretical) rather than near 1.0.
- **`radialBranchChance` was re-pointed at frontier-selection strategy**, which is the Growing Tree algorithm's actual defining knob (newest-entry = twisty/backtracker, random-entry = bushy/Prim's). The first attempt made it an "immediately grow another child" burst mechanic, which measured as having *no* effect — because re-queuing the just-grown node plus the newest-first selection bias already produced the same behavior. When a knob shows no measurable difference between 0 and 1, suspect redundancy with something else rather than assuming the test is wrong.
- **Two "intentional closeness" cases must be exempt from collision detection, and both were found the hard way** (each silently strangled growth into a tiny stunted map): (1) the initial arms fanning out around the hub — adjacent 45°-apart directions at radius ~1 sit only ~0.77 units apart, well inside a 1.5 collision radius, so most of the requested arms were being silently dropped as "collisions" with each other; (2) hamlet cluster members, which sit ~0.35 units apart by design — every direction a cluster member tried to grow found its own sibling as "nearest," so clusters could never grow further and high `radialClusterChance` produced *fewer* nodes than low. Cluster membership is tracked in a `clusterGroupOf` map purely so `nearestCollision` can skip same-group nodes. **Any future "nodes are deliberately placed close together" feature needs the same exemption.**
- **Radius is circular; validator invariant 4's forbidden band is square.** Bucketing zones purely by radius fraction let diagonal-direction nodes clear the "mid" threshold while still sitting inside the inner-40% *box*, producing real boundary-placement violations across seeds. The fix is the same explicit `fx`/`fy` box check (`boundaryAllowedAt`) the grid algorithm already uses in `midZoneBoundaryAllowed` — keep both; the radius bucket alone is not sufficient.
- **Grid sizing is by area, from node count alone — not arms × steps.** Organic growth's extent depends on how many nodes it holds, not how many arms it started with. The arms-based formula (even with a 1.5× slack factor) over-sized the grid so badly that the maze filled about a third of it: dead canvas margins, and nodes never reaching the outer radius bands where boundary markers are placed (so `boundaryFraction` looked broken). `withinBounds` must also clamp to exactly `[0, side-1]` — the coordinate range the canvas/exporter project and the validator computes fractions against — or nodes clip off the rendered edge.
- **A note on visual verification:** when screenshotting exported SVGs, make the headless-Chrome window wider than the SVG's scaled width (a 1200-wide SVG at 1.3× needs >1560px) or the right side gets cut off and looks like a generator bug. That cost a round of false debugging here.

## Notes on M4.8 (radial core-out generation algorithm — original implementation, since corrected above)

- **This is the first genuinely new `placementAlgorithm` mode field in the project** — deliberately different from every "preset" pattern built so far (region presets, `applyRecommendedGridSize`), which all have **no mode field** by design since they only ever set concrete values in existing params. Radial is a real, different code path (different placement geometry, different edge-building logic entirely), so a mode field is the honest model — don't try to force a future similar feature into the "no mode field" pattern just because that's been the house style; check first whether it's actually a different algorithm or just a different value combination.
- **`core/generationShared.ts` is a new third module, not a dependency between the two generator files.** Both `core/generator.ts` (the "grid" path) and `core/radialGenerator.ts` (the "radial" path) import classification/connection-type/direction-degree/connectivity-repair logic (`classifyNode`, `connectionTypeFor`, `pickBiome`, `pickCivilianScale`, `ensureMinimumDegree`, `repairConnectivity`, `bestAvailableDirection`, `jointlyFreeDirection`, etc.) from it — neither generator file imports from the other. This was a deliberate anti-circular-dependency decision: `generator.ts` must import `radialGenerator.ts` to dispatch to it, so `radialGenerator.ts` importing back from `generator.ts` would create a cycle. If a future third placement algorithm needs any of this logic, it goes through `generationShared.ts` too, never through another generator file.
- **`classifyNode` (in `generationShared.ts`) refactors `placeNodesGrid`'s old inline type/subtype/boundary/coastal logic into a shared, geometry-agnostic function** — parameterized by a `Zone` ("center"/"mid"/"edge") that each algorithm computes from its own geometry (grid: rectangular col/row banding; radial: radius fraction from the core). Verified this refactor doesn't change grid mode's own RNG call sequence at all (the existing "produces identical structural output for the same seed and params" test still passes bit-for-bit) — the extraction was a pure reorganization, not a behavior change, even though `ALGORITHM_VERSION` still bumped (new capability, per the same "bump for new capability even if the default path is unchanged" discipline M4.6's retrospective note already argues for).
- **A real bug caught mid-implementation: radial's grid size is *derived*, and `generateMap` must stamp it back onto the returned map's `params`.** Radial computes its own `gridCols`/`gridRows` from `targetNodeCount`/`radialSpokeCount` (`recommendedRadialGridDimensions`, `core/geometry.ts`) rather than reading the input params' `gridCols`/`gridRows` at all. Initially this function returned only `{nodes, edges}`, leaving whatever stale `gridCols`/`gridRows` sat in `draftParams` on the final `WorldMap.params` — which would have silently broken the validator's boundary-placement invariant (it computes `fx`/`fy` fractions against `map.params.gridCols`/`gridRows`), the share-code codec (which encodes exactly those fields), and the canvas/exporter's margin math. Fixed by having `generateRadial` return `gridCols`/`gridRows` alongside `nodes`/`edges`, and `generateMap` builds an `effectiveParams` object with those stamped in before it becomes the returned map's `params`. **Lesson:** any param that a placement algorithm computes/overrides internally rather than reading verbatim needs to flow back into the final `WorldMap.params` — nothing downstream can be trusted to re-derive it.
- **Also caught mid-implementation, not planned up front: I initially wrote the dispatch in `generateMap` as `placeNodesGrid(params, rng)` called twice** (once directly, once nested inside the `buildEdgesGrid` call) instead of once — an easy mistake with inline ternary dispatch that would have silently produced two different, disconnected node sets. Caught by re-reading the diff before running tests, not by a failing test (the bug would likely have still passed most invariant checks, just wastefully). Fixed by extracting a small `generateGrid(params, rng)` helper that calls `placeNodesGrid` exactly once. **Lesson:** when refactoring a direct sequential call chain (`const nodes = f(); const edges = g(nodes)`) into a branching dispatch, extract each branch into its own named function first — don't try to inline both calls into one ternary expression.
- **Core interconnectivity and the convergence pass are the algorithm itself, not "variants."** The user was explicit that ring-connection falloff and the close-paths-should-connect pass are the actual requested mechanism (not optional flavor), while `radialBranchChance`/`radialClusterChance`/`radialDeadEndPoiBias` are the genuinely optional embellishments (a fourth, `waviness`, was proposed and explicitly deferred). Don't describe `radialCoreInterconnectivity`/`radialConvergenceRadius` as "variants" in future work — they're load-bearing.
- **`radialDeadEndPoiBias` retyping must happen strictly between skeleton construction and `ensureMinimumDegree`'s degree-2 top-up** — a node's dead-end-ness (degree exactly 1) is only observable at that exact point in the pipeline; after the top-up runs, no node is ever degree 1 anymore, grid or radial. This ordering constraint is the entire trick to the feature and is easy to accidentally break if the pipeline gets reordered later.
- **Testing RNG-conditional variant knobs (branch/cluster/ring chance) required a different testing philosophy than exact-output diffing.** Each of these rolls consume `rng()` regardless of the chance value, but the *conditional body* (creating an extra node/edge) only consumes further `rng()` calls when it actually fires — so two runs with the same seed but different `branchChance` values diverge in their entire downstream RNG sequence the moment the first branch fires, not just in "does this one branch exist." A same-seed pairwise diff between low/high settings is therefore fragile and not meaningful. Tests instead compare aggregate statistics across a batch of ~10 seeds (e.g., "higher branchChance produces more total nodes on average") — the same philosophy the existing biome-weighting tests already used ("a zero-weight biome never appears" is a structural guarantee, not a byte-identical comparison), just applied to a new kind of knob.
- **`radialSpokeCount` direction selection is itself seed-driven** (shuffle `ALL_DIRS`, take the first N) rather than always picking a fixed canonical subset — consistent with the grid algorithm's own "which cells fill first is seed-driven, not top-left-first" philosophy, so spoke *count* alone doesn't fully determine spoke *placement*.
- **Verified visually via the same headless-Chrome-screenshot practice as every prior generator milestone**: default (8 spokes), zero-ring "bare spokes" (4 spokes), forced-dense-ring, forced-branch/cluster ("flavorful"), and an 80-node case all screenshot as expected — a clear central hub, visibly tapering interconnectivity from center to edge, organic branch/cluster shapes, and a readable structure even at the largest node count.

- **This is a deliberately narrow mitigation, not a fix, for the direction-mislabel bug that motivated it.** The user considered three directions (scale the grid to node count, an entirely separate placement algorithm, a finer 16-point internal compass model with 8-point display) and picked only the first. `ensureMinimumDegree`/`bestAvailableDirection`'s direction-fallback logic is untouched — the Delta-1/Ruin-3/Swamp-8-style case (two neighbors at nearly the same true bearing from a third, only one can claim that compass slot) can still occur; it's just less likely with more breathing room between nodes. Don't describe this as "the direction bug is fixed" — it isn't.

Aspect-ratio/portrait-landscape shape control was the *other* rejected-for-now idea (a separate placement algorithm) — don't fold that in here without a separate discussion.

## Notes on the `repairConnectivity` nearest-pair fix (`ALGORITHM_VERSION 2.1.1`, post-M4.7.2)

- **Root cause, precisely:** the old merge strategy sorted components by size and always attached "whichever isn't currently largest" (`rest[0]`) to "the largest" (`main`) — a purely size-ranked pairing with zero geographic awareness. On a sparse map with several small isolated pockets sitting near each other but far from whatever the largest component happened to be, each pocket paid the *full* cross-map distance to reach "main" on its own turn, one at a time, instead of ever being allowed to consolidate with its actual nearest neighbor first (which was usually another small pocket, not "main"). Found via a user-reported share-code URL, traced by regenerating the exact map and tracing `repairConnectivity`'s merge sequence directly (see the commit for the throwaway trace approach — not left in the codebase).
- **The fix is true nearest-component-pair (single-linkage) merging** — at each step, find the closest node pair across *any* two current components (not just biggest-vs-2nd-biggest) and merge those two. Verified on the exact reported case: the ~10.6-unit edge is gone entirely, and the longest edge anywhere on that regenerated map is now 2.96 units — in line with every other edge.
- **This is a real behavior change for existing seeds**, not just a quality improvement with no observable effect — `ALGORITHM_VERSION` bumped to `2.1.1` accordingly. The bridge-edge *count* is unchanged (still exactly `componentCount - 1` merges), but *which* node pairs get bridged differs, which can shift `connectionTypeFor`'s `rng()` draws for the remainder of generation. A share-code link generated before this fix will no longer reproduce byte-identically after it — expected and unavoidable, same tradeoff every prior `ALGORITHM_VERSION` bump made.
- **Deliberately scoped as a small, isolated, single-purpose change** per explicit user request ("very reversible") — touches only `repairConnectivity` itself, nothing else in the file, so `git revert` on this commit cleanly undoes it if it doesn't hold up in practice.
- **A bigger, explicitly-deferred question is on the table:** the user questioned whether constraining generation to a logical `gridCols × gridRows` grid at all is actually helping, versus a more freeform continuous layout — but asked to land this targeted fix first before opening that up. Don't start redesigning the grid model without that conversation happening first; it's flagged, not resolved.

## Notes on M4.7.1 (shareable map links — implemented)

- **"Hash" was the wrong word for what got asked for, and it's worth remembering why.** A cryptographic hash (SHA-256, etc.) is one-way — it can't be "decoded into its parts." What got built is an **encoding**: a fixed-order 15-byte packing of `GenerationParams` (version byte + seed + shape/bias/fraction fields + a flags byte), base64url-encoded into the `map` query param. If this terminology comes up again elsewhere in the project, correct it the same way.
- **`seed` never needed separate treatment** — it's already a field of `GenerationParams`, so "encode the params" already covers it. Don't reintroduce a separate seed-plus-hash design if this comes up again.
- **The five single-slider fraction fields (`edgeDensity`, `checkRequiredFraction`, `boundaryFraction`, `wildernessWaterFraction`, `settlementOutpostFraction`) are encoded as exact integer percentages (0–100), not generic fixed-point** — `GeneratePanel.tsx`'s sliders only ever produce `v/100` for integer `v`, so storing the integer and dividing by 100 on decode reconstructs the *exact* float, with zero risk of an encoding epsilon flipping one of the many `rng() < fraction` comparisons the generator makes. `nodeTypeBias` uses ordinary lossy fixed-point instead (2 of the 3 shares, third derived + renormalized, mirroring `rebalanceNodeTypeBias`'s own drift guard) since `rebalanceNodeTypeBias`'s proportional rescale never produces round percentages anyway — lower-stakes regardless, since `nodeTypeBias` only ever feeds a rounded budget calculation, not a raw RNG comparison. If a new slider is ever added to `GeneratePanel.tsx` that's a simple `v/100` control, encode it the same integer-percent way, not fixed-point.
- **`PARAMS_CODEC_VERSION` (in `core/shareCode.ts`) is deliberately a separate version number from `ALGORITHM_VERSION`** — one tracks the encoded byte layout, the other the generator's RNG sequence. They'll likely keep bumping together in practice (a `GenerationParams` shape change tends to trigger both, as it will next time), but don't conflate them into one constant.
- **`btoa`/`atob` are used for base64, not a library** — confirmed available as globals on Node v24 (this environment) and every current browser, the same cross-runtime assumption `crypto.randomUUID()` already relies on in `generator.ts`/`prototypeMap.ts`. If this project's runtime target ever drops below Node 18, revisit.
- **No version-mismatch/decode-failure banner was built** — deliberately deferred, matching Section 13's existing (also unbuilt) algorithm-version-mismatch banner. A bad share code just logs a console warning and falls through to localStorage/prototype-map. If a banner ever gets built for one, build it for both at once — it's the same UI pattern.
- **"Copy Link" copies `window.location.href` directly** — it does not call `encodeParams` itself. The address bar is already kept in sync by `generate()`/`loadMap()` via `writeShareCodeToUrl`, so the button is a convenience, not the only way to get a working link.
- **Verified end-to-end, not just via the codec's own round-trip:** `shareCode.test.ts` has a test that calls `generateMap()` on the original params and on `decodeParams(encodeParams(params)).params`, then diffs the normalized output — this is the actual user-facing promise of the feature (a shared link reproduces the *map*, not just the params object), and it's a stronger check than the plain codec round-trip tests.

## Notes on M4.7 (visual layers and node shape/color revamp — implemented)

- **The terrain-wash grouping bug (found, not just built around):** the first implementation of `generateTerrainZonesStep` grouped every node sharing a biome into one zone map-wide, with no distance limit. Since biome assignment is independent of position, this produced one hull per biome spanning nearly the entire grid — six-plus overlapping translucent blobs covering almost the whole map, unreadable. This was **not** caught by any test — it was caught by actually rendering a generated map to an image and looking at it (see Current Status above). Fixed with `clusterBySpatialProximity` (union-find over pairwise distance, `TERRAIN_CLUSTER_RADIUS = 2.2`): a biome present in two separate parts of the map now yields two separate zones, not one. There's now a regression test (`generator.test.ts`, "clusters terrainZones by spatial proximity") asserting no zone's member-node span exceeds 60% of the grid diagonal — loose enough to allow a real regional cluster, tight enough to catch the map-spanning-blob failure mode if it recurs. **Lesson for future rendering work in this project:** a test suite passing and a build succeeding do not mean generated visual output looks right — render something and look at it before considering rendering-layer work done.
- **`core/geometry.ts`** (`convexHull`, `padHull`, `centroid`) is a new pure-math core module, re-exported from `mapStore.ts` for `TerrainWash.tsx`/`FactionTerritory.tsx` to use (components can't import core/ directly — same pattern as `core/taxonomy.ts`'s re-export). `exporter.ts` imports it directly since exporter.ts is itself core.
- **Node shape/color table changed entirely** (spec Section 10b): settlement is now a yellow square (civilian) or yellow diamond (outpost) — squares/diamonds freed up from the old mountain/poi shapes since mountain left as a boundary marker and poi became a triangle. Wilderness is colored by its `Biome` subtype (six distinct colors, reusing the terrain-wash hues as solid fills) with land as a plain circle and water as a circle+ring (kept the ring deliberately — river_ford/sea_route edges are also blue, and the ring keeps a water *node* from reading as a water *edge* at a glance). Poi is uniformly a purple triangle regardless of `PoiKind` (ruin/dungeon/lair/landmark) — one look per Tier 1 type/fork, subtype available on hover/click, not encoded as a fourth color.
- **Plains (`#C9C93D`, muted yellow-green) was deliberately chosen paler than settlement's gold (`#F2C14E`)** so a plains wilderness circle and a settlement square don't read as "the same color, different shape" — flagged in the spec as a real collision risk given both are "yellow" family colors, worth a look if it still feels too close in practice.
- **Faction territory rendering has no editor to produce data yet** (Faction authoring UI doesn't exist) — it's only reachable today by hand-authoring `extensions.factions` into a JSON file and using `GeneratePanel`'s existing Import JSON button. That's enough to prove the render path works (and is covered by an `exporter.test.ts` test that constructs a `Faction` inline), but nobody will see it organically until an editor exists.
- **Layer-visibility state lives in `MapCanvas.tsx` as local `useState`, not in `mapStore`** — per spec Section 10b, toggling a layer is a pure UI concern that must never touch `WorldMap` data or the undo stack, so it doesn't belong in store state.

## Notes on M4.6 (generator capability expansion — implemented)

- **A shared `core/taxonomy.ts` module was added** (`BIOMES`/`WATER_FEATURES`/`CIVILIAN_SCALES`/`OUTPOST_KINDS`/`POI_KINDS` sets, `isWaterBranch`/`isOutpostBranch` predicates) — this is the third real use site for "infer the Tier 1.5 fork from `subtype`'s value" (`generator.ts`, `NodeShape.tsx`, `exporter.ts` all needed it), so it was extracted rather than left as three independently-drifting copies. **Important architectural detail:** `components/canvas/NodeShape.tsx` cannot import `core/taxonomy.ts` directly — the UI layer may only import `store/`/`types/`/React (spec Section 2). `isWaterBranch`/`isOutpostBranch` are re-exported from `store/mapStore.ts` for that reason; don't "simplify" this by having a component import core directly.
- **Civilian settlement scale is weighted (village 45 / town 35 / city 15 / metropolis 5) with a hard cap** (`MAX_CITY_OR_ABOVE = 2`) rather than pure weighted-random — the spec calls for "rare" city-or-above regardless of map size, and probability alone doesn't guarantee that on a large map. The cap forces village/town once 2 city-or-above settlements exist.
- **Boundary reason is now a real uniform pick among all four values** (`coastline | mountain_range | canyon_void | magical_barrier`), superseding M4.5's mountain_range-only placeholder. `markCheckRequired`'s "always check-required" rule was narrowed to specifically mean *mountain_range* paired with another boundary/wilderness node — under M4.5 this was written as "any two boundary-marked nodes," which was equivalent when only one reason existed but would have been wrong now (two unrelated boundary reasons, e.g. one coastline + one canyon_void, shouldn't unconditionally force a check).
- **`coastal` is independent of `boundary.reason === "coastline"`** — always true when that reason is present, but also assigned at a low independent rate (`INDEPENDENT_COASTAL_CHANCE = 0.05`) elsewhere, so coastal flavor and `sea_route` eligibility aren't confined to the boundary ring.
- **`generateTerrainZonesStep` groups by matching Biome value across the whole map, not spatial proximity** — one zone per biome present (≥2 members), plus one `ocean` zone if ≥2 coastal nodes exist. This is a deliberate simplification: proper spatial clustering into multiple disconnected same-biome zones is more sophistication than a first pass needs, and it's easy to evolve later without changing the `TerrainZone` shape.
- **Extension invariants (spec Section 3b) were implemented in `validator.ts` for the first time in this milestone** — `extension-node-ref`, `extension-edge-ref`, `faction-membership-unique`, all warn-only. They existed only as spec prose before now because extensions were always empty pre-M4.6; there was nothing to check.
- **Labels now derive from the Tier 2 subtype** (`"Village-1"`, `"Forest-3"`, `"Monastery-2"`) instead of the bare Tier 1 type, per spec Section 7 Step 1 — this changes generated (not hand-authored) labels from M4.5's behavior.
- **`GeneratePanel.tsx` gained three new controls** (`wildernessWaterFraction`/`settlementOutpostFraction` sliders, a `generateTerrainZones` checkbox) since these params are functionally meaningful now — leaving them unreachable from the UI would make the new capability invisible in the running app.

## Notes on M4.5 (taxonomy migration — implemented)

Read spec Section 3c before touching `NodeType`, `NodeSubtype`, `BoundaryMarker`, or `TerrainType` — it's the authoritative explanation of the tiered model (Tier 1 / Tier 1.5 fork / Tier 2 / Boundary / Tier 3+) and the fork-vs-additive-feature heuristic for extending it later. Highlights, since this reworks types that M1–M4 already shipped against:

- `NodeType` shrinks from 5 values to 3: `settlement | wilderness | poi`. `mountain` is gone entirely — it's now a `mountain_range` `BoundaryMarker`, an orthogonal fact any node can carry, not a type. `water` is gone as a top-level type too — it's a Tier 1.5 fork *inside* Wilderness (land vs. water), inferable from which subtype union a node's `subtype` belongs to (no separate branch field).
- Settlement gets the same Tier-1.5-fork treatment: civilian (scaled `village|town|city|metropolis`) vs. outpost (categorized by purpose: `monastery|military_fort|trading_post|mining_camp|waystation`). A settlement's "size" and "is it a specialized outpost" are different questions, not one scale with outpost at the bottom.
- **The generator-capability rule inverted from the original spec, not just expanded:** the old spec said the generator never touches `subtype`/water/extensions — full stop. The corrected rule is the generator *is* capable through Tier 2 (any `NodeType`, fork, and `NodeSubtype`) plus `BoundaryMarker`, and optionally `TerrainZone` data behind a new `generateTerrainZones` param. Only Tier 3+ detail (a specific ruin flavor, `grove` under `forest`, architectural settlement style) and all `Faction` data stay permanently, deliberately manual — that's not "not yet built," it's a permanent line (political texture is the DM's voice, not the algorithm's).
- `hills`/`canyon` were seriously considered as new node-level "terrain feature" values and explicitly rejected in favor of folding into the existing (zone-only) `ElevationHint` field — one topography axis, not two overlapping ones. `coastal` stayed a real per-node field specifically because it drives `sea_route` assignment on every map, not just ones using terrain zones.
- `TerrainType` (Section 3b) now literally reuses `Biome` (Section 3a) via `Biome | "coast" | "lake" | "ocean"` rather than an independently-drifting list — this creates a circular type-only import between `map.ts` and `extensions.ts`, which is fine (erased at compile time) but don't "fix" it by duplicating the union.
- `ALGORITHM_VERSION` bumps to `2.0.0` in M4.5 — this is a breaking data-model change (Section 4's versioning rule), not a minor RNG-sequence tweak.
- M4.5 and M4.6 are deliberately split: M4.5 is types + the mountain→boundary-marker migration only (must happen together since `generator.ts`/`prototypeMap.ts` won't compile against the new types otherwise) — no new subtype variety yet. M4.6 is where water/biome/civilian-scale/outpost-kind/poi-kind/terrain-zones actually start getting placed. Don't collapse these into one milestone — M4.5 alone is already a full-codebase migration touching generator/validator/prototype/rendering/exporter/every test file.

**Implementation decisions made while executing M4.5** (beyond the spec's literal text):

- **`placeNodes` got genuinely simpler, not just migrated.** Since all three Tier 1 types are now zone-uniform (zone only gates `BoundaryMarker` probability, not type eligibility — spec Section 7), the old per-zone eligibility-list-plus-force-fill machinery (`CENTER_ZONE_TYPES`/`MID_ZONE_TYPES`, the settlement/mountain quota mechanism from M2) is gone entirely. Type assignment is now a shuffled bag sized exactly to each budget (`round(nodeCount × share)`), zipped one-for-one against the already-shuffled cell order — hits the target split exactly, every seed, with far less code. Verified across 4 seeds: settlement/wilderness/poi land on exact target counts (10/27/12 for the default 20/55/25% bias) every time.
- **Only `mountain_range` is ever placed as a boundary reason in M4.5** — deliberate, not an oversight. `coastline`/`canyon_void`/`magical_barrier` need coastal/terrain awareness that doesn't exist until M4.6; picking among all four uniformly now would just be noise with no signal behind it. `generator.test.ts` has an explicit test asserting this (`only ever places mountain_range boundary markers`) — when M4.6 adds real reason variety, that test's assumption must be revisited, not just deleted.
- **Mid-zone boundary markers use a `MID_ZONE_BOUNDARY_DAMPING = 0.15` multiplier** on top of `boundaryFraction`, gated by the same `midZoneBoundaryAllowed` geometric safety margin the old `midZoneMountainAllowed` used. Not deeply tuned — flagged in the spec itself as "no evidence yet a different weighting is needed."
- **Rendering (`NodeShape.tsx`, `exporter.ts`) infers the Tier 1.5 fork from `subtype`'s value**, exactly as spec'd — `isWaterBranch`/`isOutpostBranch` check membership in the `WaterFeature`/`OutpostKind` value sets. Since M4.5 never assigns those subtypes, every settlement currently renders as civilian (large circle) and every wilderness node as land (plain circle) — the fork-aware code paths are correct but practically dormant until M4.6 starts populating `subtype`. Don't be surprised the outpost/water shapes don't show up yet; that's expected, not a bug.
- **`prototypeMap.ts`'s `RAW_NODES` data itself was not touched** — it still says `type: "mountain"` / `type: "ruin"` in the transcription (kept for source-fidelity/readability against the original HTML), and a new `resolveType()` function maps those raw labels to the current `{ type, boundary }` shape at build time. Don't "clean up" `RAW_NODES` to say `wilderness`/`poi` directly — that would erase the useful historical context of *why* those 22 nodes are boundary-marked.
- **`names.ts`'s old `mountain`/`ruin` name pools folded into `wilderness`/`poi` respectively** (matching the type migration); the old `water` pool became a standalone `WATER_FEATURE_NAMES` export, not part of `NAMES_BY_TYPE`, since water isn't a `NodeType` key anymore.

## Notes on M2 (decisions made beyond the spec's literal pseudocode)

The spec's generator/prototype description left some real gaps; these were resolved rather than left to chance, and are worth knowing before touching `generator.ts` or `prototypeMap.ts` again:

- **`core/prototypeMap.ts` is a new file, not in the spec's Section 2 file list.** It converts the 49-node dataset embedded in `docs/overworld-map.html` into a real `WorldMap` — needed both for the validator's "known-good map" test and M3's demo-map render. Added because building the same conversion twice (once ad hoc for tests, once "for real" in M3) would just invite drift.
- **The two reference docs disagreed with each other** on which edges are check-required (one edge each way) and the source data had 3 literal duplicate edges plus one node (Saltwick) with two exits both labeled SW. `docs/node-reference.md`'s table was treated as authoritative where the two disagreed; duplicates were removed; Saltwick's less-exact SW exit was relabeled to the nearest actually-free direction. Two nodes (Far Spur, Highfell East) had *every* connection marked check-required, which invariant 6 forbids — fixed with the same "unmark the lowest-difficulty edge" policy the generator itself uses (now exported as `enforceNonCheckRequiredExit` so both places share one policy).
- **The prototype still trips the warn-only direction-symmetry rule (invariant 7) in ~20 places** — real artifacts of hand-drawn data. Per spec Section 9 that rule is explicitly non-blocking, so `validator.test.ts` checks the prototype against the six hard invariants only, not that one.
- **`mountainEdgeFraction` and `nodeTypeBias.mountain` fought each other.** A 1-cell-thick edge ring is naturally ~40% of a modest grid's area, so an independent per-cell roll at 70% (the mountainEdgeFraction default) produced far more mountains than `nodeTypeBias.mountain`'s 22% share implied — and starved settlement/ruin's remaining budget in the process. Reinterpreted: `nodeTypeBias.mountain` sets a global mountain *budget* (`≈round(nodeCount × share)`); `mountainEdgeFraction` controls how much of that budget concentrates on the perimeter (edge-zone cells are processed first) versus spilling into the mid zone, rather than being an independent probability. This matches the concept doc's own framing of "frequency" and "containment" as two separate dials.
- **Settlement is placed only in the center zone** (per spec), which is a minority of the grid — left to organic weighted rolls, wilderness's larger weight consistently crowded settlement down to ~4% of the map instead of its 18% target. Fixed with a quota that gets force-filled once remaining center cells run low relative to remaining settlement need, so the target is actually met rather than just "allowed." Verified across 8+ seeds: settlement and mountain now land on target exactly every time; wilderness/ruin vary normally around their targets (no quota needed there — the miss wasn't structural).
- Center-zone "inner 50% by area" (Section 7, Step 1) is a **different, much wider band** than invariant 4's "inner 40%" mountain-forbidden band (Section 9) — these were conflated in an early draft of `classifyZone`, which starved settlement further. Now: center zone ≈ inner 70.7% per axis (`sqrt(0.5)`), invariant 4's band is untouched at 40%.
